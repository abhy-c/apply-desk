# Application portal preflight

The portal panel prepares visible-browser access; it is not an OAuth integration or an employer ATS API connector. Never ask for passwords, cookies, browser storage dumps or API keys. Do not export/import browser sessions. Reuse the host-supported browser chosen by the user. Signed-in Chrome and the in-app browser have separate sessions; a login in one does not establish a login in the other.

For a portal_check request, read its current state and portal_revision. Stop if cancelled, removed or changed. Use portal entry_url and browser choice from private state. Read the installed Job Apply instructions if available; use the host's complete Browser instructions and resolve the existing tab for the selected URL. No new browser framework is required. If the host integration is missing, explain the missing capability and offer a supported plugin through the host's actual plugin discovery tools, existing tools or a manual fallback. Do not claim a store listing or install without explicit authorization.

This check has read-only scope: open the approved page, inspect labels and whether the user is signed in or no account is required, and inspect the browser tool's supported upload capability. Do not read the applicant profile, enter form values, upload a file, accept terms, create an account or submit. Login, MFA, passwords, CAPTCHA and account creation belong to the user. Set the request waiting_user while their input is needed; stop work until they explicitly resume. Record needs_login when applicable rather than claiming a connection succeeded.

Confirm the observed HTTPS origin. If a page redirects to another employer/origin, stop and have the user add/approve that portal; a saved check is not cross-origin permission. Workday accounts can be employer-specific. Embedded Greenhouse/custom domains need their own reviewed origin and actual form check. A known hostname selects guidance, not proof of compatibility. Unknown portals are manual/guided until verified; no selectors or auto-fill path should be invented.

After observing the result, call portal-receipt with only id, revision, observed_origin, browser (supported/missing/unknown), page (accessible/blocked/unknown), auth (signed_in/not_required/needs_login/unknown), uploads (supported/manual/unknown), final_action_taken false, profile_read false and resume_uploaded false. No page text, field values, session identifiers or screenshots go in the receipt. Set the request complete only after recording a result. A blocked check can be completed with its blocker explained; the portal remains blocked.

Preflight passed means browser access/capability was observed, not that the user's profile is set up or a real application was tested. Checks expire after seven days or a Job Apply revision change. Regardless of timestamp, recheck page identity, authentication, exact approved resume and visible controls for each application. Then follow handoff.md under separate application authorization. No final submission. Forgetting a saved check does not sign out, revoke browser permissions or delete application drafts; explain that distinction.
